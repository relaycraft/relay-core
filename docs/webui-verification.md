# Web UI 验证与缺陷记录

本文件记录 **Web UI 的验证方式**和**已被发现并修复的缺陷**。
背景：UI 这一块此前验证很少，问题积压较多；而这些问题**几乎都不是读代码能发现的**——它们只在界面真正跑起来、看到渲染结果时才暴露。

## 为什么要专门做这件事

一句总结：**读样式表看不出「字号变大后列宽撞在一起」，也看不出「两层黑底叠在一起」。**

本文件里记录的 9 个问题中：

- 「列宽碰撞」「`<body>` 黑底」「根容器黑底」「扫描器误报」——**只能靠跑起来看**
- 「状态码重复 `200 200 OK`」「`Server: 0.0.0.0:0` 假地址」——**看图才像问题**，纯代码审查会认为 `{status} {status_text}` 完全正常
- 「整个界面是等宽字体」——**看图才察觉**，而且它还掩盖了一个**死代码 bug**（见下）

## 靶场

```bash
./scripts/ui-fixtures.sh [输出目录]     # 默认 /tmp/relay-core-ui
```

它会：

1. **先构建 Web UI，再构建内嵌它的 CLI**；
2. 起一个即用即弃的实例（端口 18080-18099，退出时清理）；
3. 灌入**值得看的流量**：中文、emoji、404/500、302、gzip、二进制、大 body、六种方法、慢响应、**h2c 的 gRPC 形态（带 trailers）**、真实 TLS；
4. 启动带调试端口的无头 Chrome；
5. 用 `scripts/ui-snapshot.mjs` **点击驱动**界面并截图（6 视图 × 2 主题 + 命令面板 + 帮助浮层），并**测量** computed style。

**只看几个 200 会掩盖界面的大部分 bug**，所以流量刻意做得很杂。

### 两个关键教训（都写进了脚本注释）

- **必须点击，不能改写页面。** 早期为了截亮色主题，往 HTML 里硬写 `data-theme="light"`——**什么也证明不了**，因为 app 启动时 `initTheme()` 会把这个属性删掉。走开关才是唯一诚实的办法，也正是它证明亮色主题**确实可用**。
- **必须构建被测的 UI。** 靶场最初只重建 CLI、**没有重建 Web UI**，于是它对着**嵌入的旧界面**截图并给出结论——**一个报告「没在运行的代码」的靶场**。修完 `index.html` 后探针仍显示旧的 `<body>` class，就是这样发现的。

### 诊断能力

`ui-snapshot.mjs` 除截图外还会：

- **测量**指定元素的 computed style（背景、颜色、字号、边框、class）；
- **扫描全页面找深色元素**——按**属性**找而不是按命名模式找。

扫描器是有来历的：曾用「猜选择器」的方式定位一个黑色面板，选择器**没匹配上**却返回 `NOT_FOUND`，看起来像「没有问题」。改成扫描属性后，它**直接点名**了元凶。

扫描器**只判定亮色主题**：暗色主题本来就是暗的，为它打印一个数字会被读成缺陷（这条也已修）。

## 方法论上的提醒

1. **搜索写错时，「没找到」没有意义。** 我两次因为搜索范围/正则写错而排除了正确线索（只扫 `webui/src` 漏掉 `index.html`；正则匹配不到 `bg-black`）。**一个匹配不到目标的搜索会返回干净结果，而干净结果读起来像证据。**
2. **先验证再动手。** 帮助浮层里 `Cmd/Ctrl+K` 与 `Cmd/Ctrl+/` 都写着「Command palette」，看着像 bug——查了 `Layout.tsx` 才确认**两个绑定都真实存在**，文案是对的。差点"修"掉一个不存在的问题。
3. **编辑放错位置时，回退重做比就地修补更快。** 插入辅助函数连续两次落错组件，把文件编成中间状态；`git checkout` 回退后用精确锚点重做，比在坏状态上继续叠补丁省时间。
4. **修完要看，不要只看测试。** 每次改动都重跑靶场并看图；`tsc` 与单测通过不代表界面没坏。

## 键盘可达性与焦点可见性

用 CDP **真实按 Tab** 遍历停靠点，再对同一元素**分别测聚焦态与失焦态**的 computed style，对比差异。
焦点环读样式表是读不出来的：它取决于元素聚焦时算什么值，而链路上任何一处 `focus:outline-none`
都会把它悄悄抹掉。

测量结果（修复前）：

```
ok  <button> "Flows (Cmd+1)" — outline auto 1px rgb(117, 203, 250)
ok  <input>  ""              — outline none 1px rgb(153, 200, 255), border
```

即：**所有停靠点靠的都是浏览器默认焦点环**（1px 浅蓝，两套主题都不匹配），而过滤框与规则页
textarea 更是 `outline: none`，只剩 **1px、50% 透明度**的边框变化——几乎看不见。

修复：`index.css` 定义 `:focus-visible`（**2px 主题强调色 + offset**），用 `:focus-visible` 而非
`:focus`，所以鼠标点击不会画出焦点环。它**故意不放进 `@layer`**：必须压过工具层的
`focus:outline-none`，而无层级规则优先于分层规则。修复后每个停靠点都是
`outline solid 2px rgb(34, 211, 238)`。

**已知且有意的设计**：flow 列表的行是带 `onClick` 的 `div`，**不可 Tab 聚焦**；键盘用户走 `j/k`
（帮助浮层里有记录）。在虚拟列表上给每行加停靠点是另一件事，没有顺手做。

### 工具自身的一次失败

焦点巡检第一版报「12 个停靠点全部没有焦点指示」——但 `tag` 是 `undefined`：`Runtime.evaluate`
没设 `awaitPromise`，返回的是 Promise 对象，字段全空，`changed` 全为假值，于是**无意义的输出被读成
了发现**。现已修（await + 健全性检查：读不到被聚焦元素时明确报 `FAILED` 并说明是工具错误而非发现）。

这与本文件开头记的两条是同一类错误：**一个测不到东西的工具，会输出看起来像结论的空结果。**

## 引擎侧：gRPC/h2 body 未进捕获（已部分修复，仍未闭环）

`TapBody` 只在 `Poll::Ready(None)` 上报 body，而**hyper 对定长 body 会在 size hint 归零后停止 poll**，
于是这些 body **完全不进捕获**。

### 两次失败 + 一次栈采样得到的精确结论

| 尝试 | 结果 |
|---|---|
| 在 `is_end_stream()` 谓词里上报 | 挂起 |
| 在 `poll_frame` 内、拿到帧后用 `is_end_stream()` 判断 | 挂起 |
| 在 `poll_frame` 内、用 `size_hint().exact() == Some(0)` 判断 | **通过**（协议测试 8/8、全量 704 通过） |

**关键更正**：这**不是死锁**。对挂起的测试做 `sample <pid>`，栈显示运行时**空闲在 `kevent`、
没有可运行任务、也没有任何锁被持有**——是**唤醒丢失**。而 `PrefixBuffer` 里根本没有锁
（只有 `retained: Vec<u8>`），所以早期"上报取锁"的推测是错的。

两次失败的**共同点**是调用了 `self.inner.is_end_stream()`：**hyper 的 `Incoming::is_end_stream()`
不是纯查询**，在 poll 内部调用它会让状态机丢唤醒。`size_hint()` 是纯查询，所以安全。

### 已修与未修

- ✅ 已修：**定长 body**（HTTP/1 常见情形）在最后一帧上报，不再漏记。
- ❌ 未修：**未知长度的 body**（没有 content-length 的 h2 流就是这种）两个信号都不触发——
  hint 永远不精确，而 hyper 经 END_STREAM 结束后不再 poll。**实测确认**：h2c 上的
  gRPC 形态交换，用上述修复后**两个方向都没有 body**。
- 因此那个端到端 gRPC 捕获测试**再次被移除**，没有留在套件里当失败用例。

### 下一步方向

需要一个**既安全读取、又对未知长度有定义**的完成信号——**由持有该交换的任务上报**，
而不是在 body 自己的 poll 里上报。这是证据指向的方向，而不是再挪一次调用位置。
