# Web UI 验证与缺陷记录

本文件记录 **Web UI 的验证方式**和**已被发现并修复的缺陷**。
背景：UI 这一块此前验证很少，问题积压较多；而这些问题**几乎都不是读代码能发现的**——它们只在界面真正跑起来、看到渲染结果时才暴露。

## 为什么要专门做这件事

一句总结：**读样式表看不出「字号变大后列宽撞在一起」，也看不出「两层黑底叠在一起」。**

本文件缺陷表里记录的问题中：

- 「列宽碰撞」「`<body>` 黑底」「根容器黑底」「扫描器误报」——**只能靠跑起来看**
- 「状态码重复 `200 200 OK`」「`Server: 0.0.0.0:0` 假地址」——**看图才像问题**，纯代码审查会认为 `{status} {status_text}` 完全正常
- 「整个界面是等宽字体」——**看图才察觉**，而且它还掩盖了一个**死代码 bug**（见下）

## 靶场

```bash
./scripts/ui-fixtures.sh [输出目录]     # 默认 /tmp/relay-core-ui
CDP_PORT=9333 ./scripts/ui-fixtures.sh  # 9222 被别人占着时（很常见，见下）
```

它会：

1. **先构建 Web UI，再构建内嵌它的 CLI**；
2. 起一个即用即弃的实例（端口 18080-18099，退出时清理）；
3. 灌入**值得看的流量**：中文、emoji、404/500、302、gzip、二进制、大 body、六种方法、慢响应、**h2c 的 gRPC 形态（带 trailers）**、真实 TLS；
4. 启动带调试端口的无头 Chrome；
5. 用 `scripts/ui-snapshot.mjs` **点击驱动**界面并截图（6 视图 × 2 主题 + 命令面板 + 帮助浮层），并**测量** computed style。

**只看几个 200 会掩盖界面的大部分 bug**，所以流量刻意做得很杂。

它**只切 6 个顶层视图**——这一点本身就是一个盲区：详情面板里的标签页（Headers / Payload / Timing / Trace）
从前从没被点过，而 #14 恰好只在那里炸。**"点过 6 个视图"不等于"点过这个界面"。**

### 两个关键教训（都写进了脚本注释）

- **必须点击，不能改写页面。** 早期为了截亮色主题，往 HTML 里硬写 `data-theme="light"`——**什么也证明不了**，因为 app 启动时 `initTheme()` 会把这个属性删掉。走开关才是唯一诚实的办法，也正是它证明亮色主题**确实可用**。
- **必须构建被测的 UI。** 靶场最初只重建 CLI、**没有重建 Web UI**，于是它对着**嵌入的旧界面**截图并给出结论——**一个报告「没在运行的代码」的靶场**。修完 `index.html` 后探针仍显示旧的 `<body>` class，就是这样发现的。

### 诊断能力

`ui-snapshot.mjs` 除截图外还会：

- **测量**指定元素的 computed style（背景、颜色、字号、边框、class）；
- **扫描全页面找深色元素**——按**属性**找而不是按命名模式找。

扫描器是有来历的：曾用「猜选择器」的方式定位一个黑色面板，选择器**没匹配上**却返回 `NOT_FOUND`，看起来像「没有问题」。改成扫描属性后，它**直接点名**了元凶。

扫描器**只判定亮色主题**：暗色主题本来就是暗的，为它打印一个数字会被读成缺陷（这条也已修）。

## 卡死与顺序：两个只有真实点击才暴露的缺陷（#14 / #15，已修复）

### #14「Trace 一点就卡死」——不是卡顿，是 Solid 的更新队列被异常打断

Rust 侧 `matched_rules` / `rule_variables` 带 `skip_serializing_if`，所以**普通捕获的 payload 里根本没有这两个键**：

```
["id","start_time","end_time","network","layer","tags","close_reason"]
```

而 `TraceView` 直接读 `props.flow.matched_rules.length`，于是抛
`TypeError: Cannot read properties of undefined (reading 'length')`。

关键在于**抛在哪里**：它抛在 Solid 的 reactive update 内部（`runUpdates`）。异常逃出后更新队列被中断，
signal 已经写入、memo/effect 却不再重新运行——**界面停在上一次渲染，之后每次标签点击都写进一个没人消费的队列**。
所以用户看到的是"卡死"：**不是死循环，也不是渲染慢，是更新图被打死了一个结。**

诊断过程也印证了这一点：CDP 截图里 `Trace` **已高亮**，面板内容却还是 `Headers` 的。

修法（三层，缺一层都不够）：

1. **把类型说真话**：`matched_rules?` / `rule_variables?` 标为可选（省略的字段不该被类型系统宣称为必然存在）；
2. **`flowTrace()` 归一化**：缺失与空都给同一个稳定结构（`matchedRules: []` / `ruleVariables: []`），调用方不再有机会读到 `undefined`；
3. **`ErrorBoundary` 兜底**：任何视图渲染抛错都只坏掉这一格，标签栏照常可用（实测把抛错读回填后，面板显示
   `This view could not be rendered.` 且其余标签点击**依然正常**，无未捕获页面异常）。

顺手做了一次全量审计：`Flow` 上**只有这两个字段在说谎**（`Trailers`、`grpc`、`resilience_trace`、`grpc_status` 原本就是防御式读法）。

### #15 顺序翻转——列表顺序有两个"作者"

服务端分页按 `Reverse(start_time_ms)` 返回，本来就是**新→旧**。而 `fullSync()` 把这一页**逐条**喂给
`upsertFlow()`，后者是 `unshift`（新条目放头部）——于是**整页被反转**。之后真实捕获又走 `unshift` 进到头部，
看起来就正常了：**"刷新后最新的在最下面，再抓一条又在最上面"**，正是用户报的现象。

修法：`syncFlows()` 独占「下标 0 = 最新」这条规则——把本地已知 flow 与该页合并进 `Map`，
统一按 `start_time_ms` 降序重建 `flows` / `flowOrder`（`upsertFlow` 与它共用 `evictOverflow`）。

前后对比（同一实例，同一页）：

```
修复前（刷新后）：/tick-11, /tick-10, /tick-9, /hello, /hello, /notfound, /tick-1, /tick-2 … /tick-8
修复后（刷新后）：/tick-11, /tick-10, … 与 API 顺序完全一致
修复后（新捕获 /tick-12）：落在下标 0
```

单测覆盖 6 条：乱序页、刷新不动实时顺序、刷新期间捕获不丢、`MAX_FLOWS` 截断等。

### 工具自身错了五次（同类教训：测不准的工具会给出自信的错结论）

1. **靶场早就没在测这个 UI 了。** 三处叠加，每一处单独看都"像是没什么问题"：
   - `relay-core run` 早已没有 `--control-port`，脚本却还传它 ⇒ 实例**启动即失败**；
   - 就绪探测用 `curl -sf`，而控制 API 要 bearer token ⇒ 一路 401，**静默烧完整个超时**；
   - 计数那行同样没带 token ⇒ 打印 `0 flows captured` 之后**继续往下跑**，于是后面所有结论都对着空界面读。
   现在：从 `proxy.log` 取 `#token=…` 带 `Authorization` 轮询，**取不到 token 直接失败**，计数为 0 **非零退出**。
2. **打开 UI 时没带 token。** 这条更隐蔽：`/` 本身能打开、界面看着完全正常，只是**列表永远是空的**。
   UI 是把 `#token=…` 片段换成 `relay_core_token` cookie 的（片段不会进服务器日志），
   不带片段就一条数据也拿不到。现在直接打开 daemon 打印的那个 URL。
3. **调试端口可能连的是别人家的浏览器。** Chrome 在 macOS 是单实例应用，**9222 常常被开发者自己的 Chrome 占着**：
   靶场新起的实例绑不上端口，而 `ui-snapshot.mjs` 会连上**已经在跑的那个浏览器**，把**对方的标签页**当成被测界面截图，
   输出一整套看上去很像结论的图。现在端口可配（`CDP_PORT`），并且**开工前先检查浏览器里有没有别人的页面**，
   有就报错退出。
4. **我自己的顺序校验量错了。** 第一版按"文本匹配行"找 flow，`/tick-1` 加 `0 ms` 同时匹配上了 `/tick-10`，
   于是它**报了一个不存在的顺序缺陷**。改成从 DOM 里读 `path` 才对。
5. **实例隔离。** 脚本补上 `RELAY_DATA_DIR`：否则第二个 daemon 拒绝启动（`another daemon already owns <dir>`，
   而那是开发者**正在用的**实例，不能杀），脚本又会把这个账算到 UI 头上。

### 事件流面板（`[event stream]`，新增）

被代理的 `text/event-stream` 是本项目里唯一**内容不在 Flow 快照上**的面板：SSE 响应可能永不结束，
所以引擎一边解析一边推事件。这也意味着要它有东西可看，三件事必须同时对上——引擎的解析器、
`sse-event` 帧、客户端的监听——而**一张空面板的截图与「真的什么都没发」完全一样**。
因此靶场加了一条 `/events` 固定流量（3 条具名 + 1 条未具名，逐条 flush），并把检查做成常驻项：
点开该 flow 的 Messages 标签页，把渲染出来的载荷读回来，要求 4 条事件都在，且**未具名那条显示为
`message`**（SSE 规范给无 `event:` 字段的事件的名字）。丢一条、或几条挤成一行，都会在这里失败。

它第一次运行就**失败了**——而失败是对的：见缺陷 #29。

### 于是把"只能人工点"的部分变成了常驻检查

缺陷 #14/#15 都是**截图看不出来**的：卡死的那一屏拍下来完全正常，顺序翻转也只是一行行的位置。
现在 `ui-snapshot.mjs` 除截图外还做五件事，任何一项失败都会**非零退出**（`ui-fixtures.sh` 随之停下）：

- **`[detail tabs]`**：逐个点开详情面板的标签页，同时读**两个东西**——标签条说哪个是打开的、下面的内容区**实际渲染了什么**。
  只读前者会漏掉这个 bug（卡死时高亮是**对的**），只读后者说不清是"没点动"还是"本来就一样"。
  两条判据：内容区与上一个标签页**逐字相同**（没有兜底时更新队列已死的表现），
  或内容区出现**兜底文案**（有兜底时异常被挡在这里，而它拍进截图里也只是一段普通文字）。
- **`[flow order]`**：把 DOM 里画出来的行与 API 那一页（新→旧）**逐行对比**，这是 #15 的直接回归检查。
- **`[live vs refreshed]`**：把**同时**来自"实时 SSE"和"刷新后的 API 页"的行**逐行比签名**，
  这是 #16 的直接回归检查——**唯一能把"同一行的两种来源"摆在一起**的地方。
- **`[payload view]`**：在 JSON body 上故意选 TEXT，再选一条二进制 flow，读**视图切换器高亮的是哪一个**
  （必须回到 content-type 默认的 HEX），并复查"同一个选择内用户的手选仍然被尊重"——#28 的回归检查。
- **`[still alive]`**：切换视图前后读 `body.innerText`，**文本没变就是更新队列已经死了**——这才是用户说的"卡死"。
- **`[page errors]`**：收集 `Runtime.exceptionThrown`，**任何未捕获异常都算缺陷**。
  这一条是根治性的：此前靶场一个异常都不收，所以一个"每次渲染都在抛错"的页面照样能产出一整套干净的截图。

顺带修掉一个**标签说谎**的问题：主题巡检循环以 `light` 结束，之后所有文件名写着 `-dark` 的截图其实都是亮色。
现在需要暗色的地方都显式设置主题再截图。

**检查项本身也验证过**（一个不会失败的检查等于没有检查）：把 #14 的那次越界读**临时注入回去**，重跑靶场——
`[detail tabs]` 立刻报

```
FAIL Trace: the view threw and was contained — pane says "This view could not be rendered.Cannot read
     properties of undefined (reading 'length')Try again"
[failed] 1 check(s) and 0 uncaught error(s)
```

并**非零退出**；撤掉注入后文件哈希与绿色那次运行**逐字节相同**（`e2abba16…`），所以绿色结论仍然成立。

这段还顺带说明了两件事：**`ErrorBoundary` 把"未捕获异常"变成了"可见的兜底文案"**，所以
`[page errors]`（0 条）**单独并不能**发现这个 bug——真正抓住它的是"内容区与上一个标签页逐字相同"这条判据；
而兜底文案本身也成了新的信号（检查项里显式匹配它）。

## #16 查询串在刷新后消失（已修复）——这是决策，不是补丁

服务端 `FlowSummary.path` 取的是 `url.path()`（**不含查询串**），客户端的实时摘要 `flowToSummary` 用的却是
`pathname + search`。于是同一请求：**实时显示 `/hello?r=11`，刷新一次变成 `/hello`。**

影响面不只是显示——客户端的 flow 过滤也在比这个字段，所以刷新会让一条 flow"换个名字"。

### 决策：改客户端，不改线上契约

先查了**谁在用 `host` / `path`**，结论是所有人用的都是同一个定义——**没有任何一处**把查询串算进 `path`：

| 消费者 | 用的什么 |
|---|---|
| 策略 / 规则匹配 | `host_str()` / `path()` |
| `flow_query` 的 `host:` / `path:` | `path()` 上的**子串**约束 |
| 存储层 | `path` 列的 `LIKE`（现已转义，见 #26） |
| MCP（`relay-core-probe` 的 `path_contains`） | 同一个 `FlowQuery.path_contains`，所以**连转义一起受益** |
| HAR 导出（`relay-core-api/src/har.rs`） | 条目 URL 取 `request.url.to_string()`（**完整含查询串**），`path()`/`query()` 只用来算 `headersSize` 的字节数 |
| Tauri 列表/详情 | `url.path()` |
| CLI / TUI | `display_path()` 同样只画 `path()`，有查询串时**只多打一个 `?` 提示**（列宽不够） |

真正的线上契约因此是：

| 字段 | 含义 |
|---|---|
| `host` | `url.host_str()`——**不含端口** |
| `path` | `url.path()`——**不含查询串** |
| `url` | 完整 URL |

于是让客户端**照做**，而不是让服务端跟着客户端的习惯改（那会牵动 Tauri / MCP / HAR 导出及其测试）。
列表行显示的目标串仍带端口与查询串，但它**从 `url` 派生**，不再借 `host`/`path` 之手——
TUI 早就是这么做的，只是它把查询串折成了一个 `?`。

### 代价（写在这里，免得下一个人再当 bug 修一遍）

- 直接在过滤框里搜 `?marker=47` **匹配不到**——`path` 里没有查询串。TUI 一直如此，现在两端一致了。
- 原始 L4（`Tcp`/`Udp`/`Quic`）没有 HTTP `url`，因此**没有可显示的目标串**；这与刷新后完全一致
  （详情面板仍显示 `server_host`/`sni`）。
- `host` 不含端口 ⇒ 以前"实时"那一列显示 `127.0.0.1:18090`、刷新后变成 `127.0.0.1`，
  正是 #16 的另一半症状，一并消失。
- 行里显示的完整 URL 仍在（`url` 字段），详情面板与 HAR 导出也都用它，**信息没有丢，只是归位**。

### 验证

靶场新增 **`[live vs refreshed]`**：把**同时**存在于"实时推送"和"刷新后的 API 页"里的行**逐行比对签名**
（时间、方法、状态、目标串、徽章），任何差异都失败。它抓到的原始证据是：

```
live:      02:48:27 | GET | 200 | 127.0.0.1:18090/tick-47?marker=47
refreshed: 02:48:27 | GET | 200 | 127.0.0.1/tick-47
```

修复后：

```
[live vs refreshed] 33 row(s) drawn twice (39 live, 39 from the API)
  ok — every row renders the same live and after a refresh
```

`duration_ms` **故意排除**在签名之外：一条仍在传输中的 flow 在两种渲染里合法地一个有一个没有。

## 这一轮顺带修掉的：同一个 bug 的多个副本

修 #16 的过程中发现，**"同一个值被推导多次"**这个病根不止一处，于是把能找到的都收敛了。

### 错误判定曾有三份实现（#19）

一条 flow "算不算错"被写了三遍，而且**三遍都不一样**：

| 位置 | 规则 | 问题 |
|---|---|---|
| `webui` 实时摘要 | 状态 ≥500、`error` 标签、`stream-reset`、`close_reason`、gRPC ≠ 0 | 最全 |
| `relay-core-runtime` 摘要 | 只看状态 ≥500 与 `error` 标签 | **少看** `close_reason`/gRPC |
| `relay-core-tauri` FlowIndex | 硬编码 `false` | **永远是"没错"** |

服务端的 `has_error` 会**存进 SQLite 并参与服务端过滤**，所以这不只是徽章画错：**同一条 flow 在实时列表里
可能被 `err` 筛出来，刷新后消失**。

修法：`relay-core-api::flow::flow_is_error(&Flow)` 成为唯一规则——实时摘要、`err` 过滤 token、服务端摘要、
Tauri 索引**四处共用**；`flow_has_error` 删除。客户端 `flowIsError()` 与它逐条对齐（含 `close_reason?.reason === 'reset'`）。

### 过滤语言曾是"另一个实现"（#17）

设计文档 §5.1 写明过滤框**复用 TUI 的 `parse_flow_filter` 语法**，但客户端实现是另写的，细节全错：
`status:404` 的比较方向、`400-499` 区间、`host:`/`path:` 的分工、不可解析 token 该"无约束"还是"不匹配"、
纯文本 token 该匹配哪些字段。现在 `webui/src/lib/flowFilter.ts` 与 `flow_query.rs` 逐条对齐，
并且**两侧各有测试**（Rust 侧新增 7 条镜像测试，专门覆盖最容易写错的边界：区间、上溢饱和、无状态行、空值 token）。

### 其他"会撒谎的东西"

- **TS 类型**（#25）：`Flow.close_reason` 类型里干脆没有（serde 是内部标签 `{"reason":"reset"}`），
  WebSocket 层把 `closed` 写成了 `open`，`FlowPage.total` 服务端**从不返回**。类型是给下一个人看的文档，
  说谎的类型比没有类型更贵。
- **存储层的过滤**（#26）：`host LIKE '%' || ?1 || '%'` 把用户输入的 `%`/`_` 当通配符，
  于是"存储查询"返回的**多于**"内存过滤"选中的。已加 `ESCAPE '\'` 与转义函数。
- **相同时间戳的排序**（#27）：`ORDER BY start_time_ms DESC` 在值相同时顺序未定义，分页会漏行/重复。
  加 `rowid` 兜底；保留策略用同一顺序，于是"留下的恰好是列表最上面那些"。

### 界面侧的"不响应"（#18 / #21 / #22 / #23 / #24）

这一组都是 Solid 的直接后果，值得单独记：

- **组件体只执行一次**，解构出来的 props 是**快照**。`HeadersView` 等直接 `const { headers } = props.flow…`，
  于是**换一条 flow 后仍渲染上一条**。改成 thunk + accessor children（`<Show>{(body) => …}`），
  非 keyed 的 `<Show>` 才会随值重建。
- **`else` 分支不会在卸载时执行**：Workshop 的轮询定时器写在 `createEffect` 之外，`onCleanup` 从不触发，
  **每访问一次泄漏一个 1 Hz 定时器**。
- **首次采样不能当变化**：状态栏把 `prevTotal = 0` 当基线，开局第一个数就是一个假的高 QPS。
- **无上限的队列**：SSE 突发时 `pendingFlows` 无界增长；现在有界（1000），溢出丢最旧并触发一次重同步。
- **断线要看得见**：`onerror` 只重连不报状态，于是"没数据"和"断了"长得一样。现在有 `disconnected` 事件，
  空态明说"Not receiving flow events — reconnecting…"。
- **选择变了，属于上一个选择的状态就该清掉**（#28）：Payload 的视图（JSON/HEX/TEXT）是一次"关于这个 body"的
  表态，默认值本来按 content-type 推导（**"图片不要用只能打印乱码的 JSON 视图打开"** 就是它的注释写的），
  但用户手选的值会跨选择留下——于是"JSON 里点 TEXT → 选一条二进制"就把字节按 UTF-8 解码了，
  下面还挂着一句"这是二进制，请用 HEX"。

  **这一条同时验证了检查项本身**：把重置那行**临时注释掉**重跑靶场，`[payload view]` 立刻报

  ```
  [payload view] picked TEXT on a JSON body, then selected a binary one: switcher says TEXT
    FAIL the payload view stayed on TEXT after selecting another flow; a binary body must open on HEX,
         its content-type default
  [failed] 1 check(s) and 0 uncaught error(s)
  ```

  并**非零退出**（`HARNESS_EXIT=1`）；恢复那行后同一靶场全绿。**一个从未失败过的检查，不算检查。**

## 靶场自身的第 6 次失败（虚拟列表）

`[live vs refreshed]` 全绿之后，脚本还是退出了：`no flow row containing "/png"`。

原因不在 UI：靶场的 tick 流量跑到 200 条，flow 列表**是虚拟化的**——行只在可见范围内才在 DOM 里。
老写法（挑不在屏幕上的行）只在捕获量小的时候碰巧成立，**流量一多就静默失效**。
现在先**用过滤框把目标行筛出来**再点（真实 `input` 事件，不是改 value），点完清空。
失败信息也改成"筛完剩 N 行，没有一行包含它"——**工具错误与 UI 缺陷必须能分辨**。

教训与前面几条同源：**一个依赖环境规模才成立的检查，会在某天安静地不再检查任何东西。**

## 方法论上的提醒

1. **搜索写错时，「没找到」没有意义。** 我两次因为搜索范围/正则写错而排除了正确线索（只扫 `webui/src` 漏掉 `index.html`；正则匹配不到 `bg-black`）。**一个匹配不到目标的搜索会返回干净结果，而干净结果读起来像证据。**
2. **先验证再动手。** 帮助浮层里 `Cmd/Ctrl+K` 与 `Cmd/Ctrl+/` 都写着「Command palette」，看着像 bug——查了 `Layout.tsx` 才确认**两个绑定都真实存在**，文案是对的。差点"修"掉一个不存在的问题。
3. **编辑放错位置时，回退重做比就地修补更快。** 插入辅助函数连续两次落错组件，把文件编成中间状态；`git checkout` 回退后用精确锚点重做，比在坏状态上继续叠补丁省时间。
4. **修完要看，不要只看测试。** 每次改动都重跑靶场并看图；`tsc` 与单测通过不代表界面没坏。

## 键盘可达性与焦点可见性

用 CDP **真实按 Tab** 遍历停靠点，再对同一元素**分别测聚焦态与失焦态**的 computed style，对比差异。
焦点环读样式表是读不出来的：它取决于元素聚焦时算什么值，而链路上任何一处 `focus:outline-none`
都会把它悄悄抹掉。

测量结果（修复前）：

```
ok  <button> "Flows (Cmd+1)" — outline auto 1px rgb(117, 203, 250)
ok  <input>  ""              — outline none 1px rgb(153, 200, 255), border
```

即：**所有停靠点靠的都是浏览器默认焦点环**（1px 浅蓝，两套主题都不匹配），而过滤框与规则页
textarea 更是 `outline: none`，只剩 **1px、50% 透明度**的边框变化——几乎看不见。

修复：`index.css` 定义 `:focus-visible`（**2px 主题强调色 + offset**），用 `:focus-visible` 而非
`:focus`，所以鼠标点击不会画出焦点环。它**故意不放进 `@layer`**：必须压过工具层的
`focus:outline-none`，而无层级规则优先于分层规则。修复后每个停靠点都是
`outline solid 2px rgb(34, 211, 238)`。

**已知且有意的设计**：flow 列表的行是带 `onClick` 的 `div`，**不可 Tab 聚焦**；键盘用户走 `j/k`
（帮助浮层里有记录）。在虚拟列表上给每行加停靠点是另一件事，没有顺手做。

### 工具自身的一次失败

焦点巡检第一版报「12 个停靠点全部没有焦点指示」——但 `tag` 是 `undefined`：`Runtime.evaluate`

这与本文件开头记的两条是同一类错误：**一个测不到东西的工具，会输出看起来像结论的空结果。**

## 引擎侧：gRPC/h2 body 捕获（已修复）

`TapBody` 原本只在 `Poll::Ready(None)` 上报，于是**两类 body 进不了捕获**：hyper 对定长 body 在
size hint 归零后停止 poll；h2 流没有 content-length，hyper 经 END_STREAM 结束且不再 poll。

现在两条路径都覆盖：定长走 `size_hint()`（纯查询），**其余（含 h2）走 `Drop`**——每个 body 都必然
到达的时刻。回调只做 O(1) 的「移动缓冲 + 交接」，framing 与更新在另一个任务里完成。

### ⚠️ 更正：此前四次「失败」与"死锁"结论**全部作废**

我曾据此写下"在 poll 里调用 `is_end_stream()` 会丢唤醒"、"`Drop` 里做重活会挂"。**这些都是错的。**

真实原因：`handle_http_request` 用 **`on_flow.send(..).await`（阻塞）**发送，而
`protocol_tests` 的辅助函数给它一个**容量 10、且从不读取**的通道。基线刚好没填满，**任何多出一条
更新的改动都会把它顶满**，代理于是永久阻塞在自己的 flow 通道上、响应发不出去。

**栈采样的误读**：我当时看到"运行时空闲在 `kevent`、无任务可运行"，读成了"唤醒丢失"——
**而一个阻塞在满通道上的 `send().await` 看起来完全一样**。这是本轮最贵的一课：
**症状相同，机制不同；栈只能告诉我它没在跑，不能告诉我它在等什么。**
